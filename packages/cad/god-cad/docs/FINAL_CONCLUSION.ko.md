# GOD-CAD 최종 결론

결정일: 2026-09-10. 입력: 사용자가 제공한 [공유 대화](https://chatgpt.com/share/6aa28833-6a2c-83e9-805f-c970c51367f7)와 동일 주제의 첨부 텍스트. 아래는 원문의 단순 요약을 넘어 개발을 시작하기 위해 정한 설계 결정이다.

## 최종 정의

**GOD-CAD는 원본 DWG의 객체 정체성을 유지하면서 기하·공간 관계·건축 의미·편집 의존성을 연결하고, AI가 제안한 변경을 CAD 네이티브 API로 실행한 뒤 다시 검증하는 도면 이해·편집 엔진으로 개발한다.**

핵심 자산은 모델 하나나 그래프 데이터베이스 하나가 아니다. **원본 객체와 의미 객체 사이의 추적 가능한 연결, 변경의 영향 계산, 검증 가능한 실행 절차**다.

## 1. 온톨로지와 그래프는 함께 사용한다

온톨로지는 벽·문·공간과 관계의 정의다. Knowledge Graph는 특정 도면에 존재하는 객체와 관계를 그 정의에 맞춰 기록한 결과다. DXF는 해당 결과를 만드는 추출 경로다. 따라서 최종 흐름은 다음과 같다.

```text
DWG/DXF 객체 추출 → 기하·위상 분석 → 증거 기반 의미 인식
→ 온톨로지에 정렬된 Knowledge Graph → 편집 의존성 분석
→ 구조화된 Patch → 네이티브 CAD 실행 → 재추출·재검증
```

표준에서 공간은 BOT, 건축 요소는 BEO의 필요한 개념을 참조한다. BOT는 W3C Linked Building Data Community Group의 온톨로지이고, 여기서 검토한 BEO는 `https://w3id.org/beo#`의 Built Element Ontology다. 이름이 비슷한 어휘나 서로 다른 버전을 섞지 않는다. [BOT](https://github.com/w3c-lbd-cg/bot), [BEO](https://cramonell.github.io/beo/actual/index-en.html).

## 2. 원본 하나에 여러 표현을 연결한다

| 표현 | 담는 내용 | 최종 역할 |
| --- | --- | --- |
| Source | 파일, revision, handle, layout, block instance, xref 문맥 | 원본 CAD와 다시 연결 |
| Geometry | 정확한 좌표·곡선·변환·단위와 계산 결과 | 기하 연산 |
| Visual | 렌더 이미지, 카메라·축척·폰트·레이어 설정 | 화면 결과 확인 |
| Semantic | Wall/Door/Room 및 각 판정의 근거와 상태 | 질문과 설계 의도 해석 |
| Edit | 갱신 의존성, 제약, 전후 상태, 실행 이력 | 수정 영향과 실행 통제 |

의미·위상·편집 그래프는 논리적으로 구분한다. 이것이 물리적으로 세 개의 DB를 설치한다는 뜻은 아니다. v0.1은 JSON과 메모리 구조로 시작한다. 그래프 DB는 실제 조회·규모 측정 후 도입한다.

한 벽은 여러 선·해치·블록으로 표현될 수 있고, 블록 정의 하나는 여러 위치에 삽입될 수 있다. 다섯 표현을 무조건 1:1로 묶지 않는다. 의미 객체와 원본 객체는 별도 ID를 사용하고 1:N 또는 N:M 근거 연결을 유지한다.

## 3. DXF와 SVG는 원본의 완전성을 보장하지 않는다

DWG 원본은 보존한다. 네이티브 추출, DXF 분석, CAD 호스트 렌더를 원본 revision에 연결하고 각 경로의 지원 범위와 누락을 기록한다. ezdxf는 DXF를 다루는 구현 도구로 채택한다. SVG 출력은 좌표 변환과 시각적 표현을 거치므로 원래 CAD 좌표나 편집 객체의 대체물이 될 수 없다. [ezdxf SVG 설명](https://ezdxf.readthedocs.io/en/stable/tutorials/image_export.html).

**같은 ezdxf 입력·파서에서 얻은 JSON과 SVG의 일치는 독립 검증이 아니다.** 두 경로가 같은 객체를 누락할 수 있다. 실제 write-back의 완료 판정에는 CAD 호스트에서 저장 후 다시 연 결과, 변경 대상과 비대상 객체의 구조 비교, 같은 조건의 렌더 비교가 필요하다.

## 4. 표준은 재사용하고 CAD 고유 정보만 확장한다

GOD-CAD가 직접 관리하는 부분은 원본 참조, 변환·매핑 증거, 의미 후보와 확정 상태, 편집 연산, 제약, 검증 이력이다. OMG/FOG의 geometry 연결 방식은 상호운용 설계에 참고하고 실제 채택 시 URI와 버전을 고정한다. FOG 자체도 모든 형식을 포괄하지 않는다고 명시한다. [FOG 공식 저장소](https://github.com/mathib/fog-ontology).

bSDD는 공통 개념과 속성 정의를 가져오는 사전 서비스다. 프로젝트의 실제 벽·문·치수와 편집 의존성이 이미 들어 있는 DB로 취급하지 않는다. 초기 코어가 bSDD 네트워크 연결에 의존할 필요도 없다. [buildingSMART bSDD](https://www.buildingsmart.org/users/services/buildingsmart-data-dictionary/).

v0.1의 실제 연결은 BEO 분류 URI와 작은 CAD 확장 TTL까지만이다. BOT/OMG/FOG 통합, RDF export, SHACL, IFC/bSDD 매핑은 후속 작업으로 관리한다.

## 5. AI는 계획을 제안하고 CAD 엔진이 실행한다

자연어 요청은 대상 조회 → 모호성 확인 → 영향 분석 → 구조화된 Patch로 변환한다. LLM이 임의 Python/LISP/C# 문자열을 생성해 즉시 실행하도록 설계하지 않는다.

예를 들어 ‘회의실을 500mm 넓혀라’에는 어느 경계를 옮길지, 인접 공간을 어떻게 유지할지, 문과 치수의 갱신 방식이 빠져 있다. 대상이 둘 이상이거나 의미가 확정되지 않으면 후보와 예상 변경을 보여주고 구체화한다.

문은 호스트를 따라 이동할 수 있지만, 치수는 참조점에서 다시 계산하고 해치는 경계에서 다시 생성해야 할 수 있다. 인접 벽은 이동이 아니라 연장·절단이 필요할 수 있다. **의존성 그래프는 영향 대상을 알려주고, 객체별 편집 규칙이 수정 방법을 결정한다.** 모든 관련 객체를 같은 벡터로 이동시키는 방식은 `MOVE_WALL`의 구현이 아니다.

초기 제품의 실제 목표 호스트는 공유 대화에 맞춰 ZWCAD/ZRX.NET으로 둔다. 공식 개발 지원 페이지에는 ZRX.NET 인터페이스가 있다. 실제 호스트 버전과 SDK·런타임 호환성은 현장 환경에서 확인한 후 구현한다. [ZWCAD 개발 지원](https://www.zwsoft.com/support/zwcad-devdoc).

## 6. ‘완벽’ 대신 범위와 근거를 관리한다

이번 검토는 모든 CAD가 완벽하게 이해된다는 결론을 지지하지 않는다. 출처 대화의 ‘70~80%’ 같은 수치는 벤치마크 근거가 없어 제품 수치에서 제외한다. 의미 점수·기하 허용오차·검증 통과 상태는 서로 다른 지표다. 레이어명은 약한 증거이며 점수 0.5는 정확도 50%라는 뜻이 아니다.

CADIR는 실행 가능한 중간 표현과 construction graph에 관한 관련 연구로 확인했다. 하지만 생성 과정에서 기록한 이력을 사용하는 접근을 기존 임의의 2D DWG에서 설계 이력이 자동 복구된다는 근거로 확대하지 않는다. 이 프로젝트에는 ‘의존성을 명시적으로 기록한다’는 원리를 참고한다. [CADIR 논문](https://arxiv.org/abs/2608.00891).

모든 건축 개념과 모든 DWG 편집 관계를 즉시 제공하는 완성형 공개 DB를 전제로 하지 않는다. 공개 데이터셋과 연구 모델은 추후 자사 도면과의 형식·분류체계·이용 조건·성능 차이를 검토해 선택한다.

## 7. 개발 우선순위

1. **식별·단위·지원 범위를 정확하게 기록한다.** 원본에 다시 연결하지 못하는 의미 인식은 편집에 사용하지 않는다.
2. **DXF 분석과 제한된 계획 시뮬레이션을 실행한다.** 이것이 이번 v0.1의 범위다.
3. **ZWCAD 네이티브 추출과 변환 매핑을 검증한다.** DXF handle과 DWG handle의 일치를 추정하지 않는다.
4. **정해진 객체·명령부터 저장 후 재검증까지 완성한다.** 원본과 별도 복사본에서 수행한다.
5. **벽·문·공간의 의미 편집과 자연어 인터페이스를 확장한다.** 표본과 작업별 성공 기준을 함께 늘린다.

최종 채택 결정은 **‘원본 참조를 유지하는 CAD Knowledge Graph + 객체별 편집 규칙 + 네이티브 실행 후 검증’**이다. 먼저 제한된 도면과 명령에서 신뢰할 수 있는 한 사이클을 완성하는 것이 GOD-CAD의 첫 제품 목표다.
